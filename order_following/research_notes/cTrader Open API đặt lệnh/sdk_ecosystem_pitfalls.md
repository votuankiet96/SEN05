# cTrader Open API — SDK Ecosystem & Community Lessons-Learned on Order Placement

## What official SDKs does Spotware provide, and what is their maintenance status?

### Takeaway
Spotware officially maintains exactly two SDKs — **OpenApiPy** (Python) and **OpenAPI.Net** (C#/.NET 6) — plus a Java *example* (not an SDK) and the raw `.proto` message definitions. Both real SDKs are effectively **dormant since mid-2024**: last substantive commits were June–August 2024, multiple open issues (including a dependency-CVE report and breaking-change reports) from 2025 and into 2026 show **no visible Spotware maintainer replies**, and Spotware's own staff have acknowledged in the community forum that the sample/SDK code was never built to production software-lifecycle standards. This is an important flag for anyone planning a 24/7 unattended production system in 2026: the official libraries are usable and free, but should be treated as lightly-maintained reference implementations, not vendor-supported production SDKs.

### Cited Findings
- Spotware's official GitHub org (`spotware`) hosts `OpenApiPy` (Python), `OpenAPI.Net` (.NET/C#), `ctrader-open-api-v2-java-example` (Java *examples*, not a full SDK), `openapi-proto-messages` (raw `.proto` files), and `Open-API-Charting-Library` — [github.com/orgs/spotware/repositories](https://github.com/orgs/spotware/repositories)
- Official getting-started docs state you can use "any programming language" to connect (raw TCP/TLS + Protobuf or JSON), but Spotware only ships/maintains SDKs for **C# and Python**; for JSON no SDK is offered because "handling serialisation and deserialisation in this case is relatively simple" — [help.ctrader.com/open-api/](https://help.ctrader.com/open-api/)
- Same page: official rate limits are **50 requests/second per connection** for non-historical requests and **5 requests/second per connection** for historical-data requests — [help.ctrader.com/open-api/](https://help.ctrader.com/open-api/)
- **OpenApiPy**: 192 stars, 63 forks, 10 open issues, MIT license, async via Twisted, ships pre-compiled proto messages — [github.com/spotware/OpenApiPy](https://github.com/spotware/OpenApiPy)
- OpenApiPy's last commits on the `main` branch are dated **August 6–7, 2024** (per commit history page) — [github.com/spotware/OpenApiPy/commits/main](https://github.com/spotware/OpenApiPy/commits/main)
- PyPI release history for `ctrader_open_api`: 0.9.2 published **June 26, 2024** is the latest non-yanked release; 0.9.3 (Aug 6, 2024) was **yanked** the next day — [pypi.org/project/ctrader_open_api](https://pypi.org/project/ctrader_open_api/)
- OpenApiPy open issues as of research date include: #43 "Pinned dependencies have 9 known CVEs — any plans to update?" (Feb 17, 2026), #39 an unhandled `AttributeError` in the SSL/Twisted connection path (May 12, 2025), #38 "Compatibility Issues with Modern Dependencies (protobuf, OpenTelemetry)" (Apr 26, 2025), #37 a `NameError` on `ProtoOAAccountsListReq` (Apr 10, 2025) — none show a Spotware maintainer response in the listing — [github.com/spotware/OpenApiPy/issues](https://github.com/spotware/OpenApiPy/issues)
- **OpenAPI.Net**: 95 stars, 52 forks, 7 open issues, MIT license, built on Reactive Extensions (Rx), targets **.NET 6 only** (not .NET Framework) — [github.com/spotware/OpenAPI.Net](https://github.com/spotware/OpenAPI.Net)
- OpenAPI.Net's last commit on `master` is **"Updated SDK to cServer 90," dated June 28, 2024** — [github.com/spotware/OpenAPI.Net/commits/master](https://github.com/spotware/OpenAPI.Net/commits/master)
- NuGet package `cTrader.OpenAPI.Net` shows version 1.4.4 (current) with 26,439 downloads, last published **May 3, 2022** — i.e. the NuGet package is even further behind than GitHub's last commit — [nuget.org/packages/cTrader.OpenAPI.Net](https://www.nuget.org/packages/cTrader.OpenAPI.Net)
- OpenAPI.Net open issues include a still-open .NET 8 support request (Aug 17, 2024), unparsed message types (`ProtoOaDealListByPositionIdRes`, Apr 25, 2024; a missing case for `ProtoOAOrderListRes` in `MessageFactory.GetMessage`, opened Sep 5, 2026), and a missing `ProtoOAGetPositionUnrealizedPnLReq` in the NuGet build (Feb 29, 2024) — none show visible maintainer responses in the issue list — [github.com/spotware/OpenAPI.Net/issues](https://github.com/spotware/OpenAPI.Net/issues)
- In a 2021 "Open API Critique" thread, a developer criticized the .NET sample's non-idiomatic naming (`_msg`, `app_auth_req`), a typo in a class name (`PotoOATraderReq`), the API forcing developers to understand low-level protocol call-ordering instead of providing clean abstraction, and undocumented "TcpIP over SSL" / Protobuf serialization requirements. Spotware staff member "Panagiotis" (PanagiotisChar, a recurring Spotware community responder) **acknowledged the criticisms were valid**, explained the sample code was a community project lacking "proper software lifecycle process," and said Spotware would build "a comprehensive SDK using proper coding and quality standards in the future." A 2022 follow-up commenter added that documentation gaps around undocumented methods create "hazardous ambiguity for production implementations," exposing traders to financial risk — [community.ctrader.com/forum/connect-api-support/32091/](https://community.ctrader.com/forum/connect-api-support/32091/) (thread dated Jan 8, 2021, with a 2022 follow-up)

### Inferences
- Given the promised "comprehensive SDK" (2021) never materialized as a separate product — OpenApiPy and OpenAPI.Net are still the same community-style libraries years later, now stale since mid-2024 — teams should not expect Spotware to proactively fix SDK bugs or respond quickly to GitHub issues; budget for forking/patching the SDK yourself (e.g., updating pinned dependencies with known CVEs) rather than waiting on upstream.
- The NuGet package lagging ~2 years behind the GitHub repo suggests installing OpenAPI.Net from source/GitHub (not NuGet) if any post-2022 fixes are needed.
- Because both SDKs are unmaintained references rather than hardened production libraries, a 24/7 real-money system should treat them as a protocol/codegen convenience layer and add its own reconnect, retry, validation, and error-handling layers rather than trusting SDK defaults.

### Gaps
- Could not confirm an exact "current open issue count" snapshot beyond what GitHub's issue list rendered at fetch time (10 for OpenApiPy, 7 for OpenAPI.Net); these numbers change continuously.
- Could not find any official Spotware statement (blog/changelog) explicitly declaring the SDKs deprioritized or explaining the mid-2024 activity drop-off — this is an inference from commit/release/issue timestamps, not a confirmed policy statement.

## What are the most notable community-maintained libraries for Node.js/TypeScript, .NET/C#, Java, Go, or other languages?

### Takeaway
Outside Spotware's own two SDKs, the community ecosystem is thin and fragmented: a handful of small, low-star Node.js/TypeScript wrappers, several competing small Go clients with essentially no adoption, and no notable independent Java or C# community library beyond Spotware's own official one. None of the community options show evidence of significant production usage (stars in the single-to-low-double digits, most with zero or near-zero issue activity, several appear to be recent/solo projects).

### Cited Findings
- **Node.js/TypeScript:**
  - `ctrader-ts` (TheCommandCat) — "Unofficial TypeScript client for the cTrader Open API — type-safe, agent-friendly, zero boilerplate," MIT license, 7 stars, 0 forks, 0 open issues, 21 total commits. Wraps high-level trading operations (market/pending orders, position management, account queries, streaming, market data) but also exposes an escape hatch (`ct.raw`) to the full protobuf layer for anything not covered by the high-level API. Explicitly says "unofficial community project · Not affiliated with Spotware." Markets itself partly toward AI-agent/LLM use cases (ships an `llms.txt`) — [github.com/thecommandcat/ctrader-ts](https://github.com/thecommandcat/ctrader-ts)
  - `cTrader-Layer` (amircp / Reiryoku Technologies) — "A Node.js communication layer for the cTrader Open API," MIT license, 5 stars, 13 forks, 0 open issues. Lower-level than ctrader-ts: connection management, promise-based command sending, event listening, HTTP-based token/account retrieval, and heartbeat handling. README doesn't state whether it covers the full protobuf surface — [github.com/amircp/cTrader-Layer](https://github.com/amircp/cTrader-Layer)
  - `@claasahl/spotware-connect-api` (npm) — architected around a Node `EventEmitter` funneling requests/responses/events — [npmjs.com/package/@claasahl/spotware-connect-api](https://www.npmjs.com/package/@claasahl/spotware-connect-api)
  - The cTrader community forum itself has threads asking "is there a legit way to connect Open API with Node.js?" and "Node.js library for using cTrader OPEN API," suggesting Node/TS tooling is a recurring gap developers ask about rather than a solved problem — [community.ctrader.com/forum/connect-api-support/37237/](https://community.ctrader.com/forum/connect-api-support/37237/), [community.ctrader.com/forum/connect-api-support/36237/](https://community.ctrader.com/forum/connect-api-support/36237/)
- **.NET/C#:** No notable independent community alternative to Spotware's own `OpenAPI.Net` was found in this research; the ecosystem here is essentially the official SDK only.
- **Java:** No community SDK was found beyond Spotware's own `ctrader-open-api-v2-java-example`, which is explicitly example/sample code (Maven-based, generates protobuf classes via a Maven plugin, requires manually wiring `CLIENT_PUBLIC_ID`/`CLIENT_SECRET`/`ACCESS_TOKEN` in a properties file) rather than a packaged library — [github.com/spotware/ctrader-open-api-v2-java-example](https://github.com/spotware/ctrader-open-api-v2-java-example)
- **Go:** The Go ecosystem is fragmented across several small, apparently low-adoption, independent projects with no single dominant library:
  - `diegobernardes/ctrader` — describes itself as a "Go SDK for cTrader Open API," requires Go 1.22+ — [github.com/diegobernardes/ctrader](https://github.com/diegobernardes/ctrader)
  - `linuskuehnle/ctraderopenapi` — "a compact, idiomatic Go client... focuses on providing a clear, testable API surface for sending requests and handling streaming events" — [pkg.go.dev/github.com/linuskuehnle/ctraderopenapi](https://pkg.go.dev/github.com/linuskuehnle/ctraderopenapi)
  - `ty2/ctrader-go`, with `MShoaei/cTrader-go` existing specifically as a fork that "fixes a small issue" in it — [pkg.go.dev/github.com/ty2/ctrader-go](https://pkg.go.dev/github.com/ty2/ctrader-go), [pkg.go.dev/github.com/MShoaei/cTrader-go](https://pkg.go.dev/github.com/MShoaei/cTrader-go)
  - `fxnity/ctrader` and `bborbe/ctrader` (the latter is just generated Go proto files, not a client) — [pkg.go.dev/github.com/fxnity/ctrader](https://pkg.go.dev/github.com/fxnity/ctrader), [github.com/bborbe/ctrader](https://github.com/bborbe/ctrader)
- **Other Python alternatives:** `ejtraderCT` (ejtraderLabs) is a Python library but targets cTrader's separate **FIX API**, not the Open API/protobuf protocol — described as "Perfect for HFT" — [github.com/ejtraderLabs/ejtraderCT](https://github.com/ejtraderLabs/ejtraderCT)

### Inferences
- The sheer number of small, competing, low-star Go clients (at least 5 independent attempts found) with no clear winner suggests the community has not converged on a trusted Go library — anyone choosing Go should expect to read/patch the source themselves rather than rely on community support.
- The repeated forum questions asking whether there's a "legit" way to use Node.js suggests Node/TypeScript is one of the least officially-supported paths despite community demand, which is consistent with there being no official Spotware Node/TS SDK at all.
- Given no library (official or community) in any language reports meaningfully large adoption (largest is OpenApiPy at 192 GitHub stars), it's reasonable to infer the cTrader Open API developer community is comparatively small relative to other broker APIs, which likely also means smaller Stack Overflow/community coverage and slower third-party bug fixes across the board.

### Gaps
- Could not find usage/download telemetry (e.g., PyPI/npm/NuGet download counts) for most community libraries beyond OpenAPI.Net's NuGet count (26.4K total downloads) and OpenApiPy's PyPI presence — star counts are a weak proxy for actual production usage.
- Could not confirm whether any of the Go libraries or `ctrader-ts`/`cTrader-Layer` have been used in any publicly documented live/production trading system; no case studies were found.
- No notable Rust, C++, or PHP community library surfaced in this research; it's unclear if any exist with meaningful adoption — treat this as an open gap rather than evidence of absence.

## For a system that must run unattended 24/7 placing real orders, what do experienced community members recommend regarding language/library choice, and why?

### Takeaway
The clearest, most consistent signal from Spotware's own official docs and community threads is: **use Protobuf (not JSON) for production**, and prefer **C# or Python specifically because those are the only two languages Spotware provides any official SDK/codegen support for** — anything else means owning your own protobuf plumbing and reconnect logic with materially less community backstop. Beyond that, there is no strong, well-evidenced community consensus singling out one specific language as definitively best for 24/7 unattended trading; the stronger and more repeated theme in the forums is about *operational discipline* (start read-only, log everything, validate before trading live) rather than language choice per se.

### Cited Findings
- Official docs: Protobuf is "binary, more compact and faster to parse, which suits production integrations and higher message rates," while JSON is recommended only "for early development," with Protobuf preferred "when latency or throughput matters" — paraphrased from official Open API developer guidance surfaced via search of [help.ctrader.com/open-api/](https://help.ctrader.com/open-api/) and related pages (see note in Gaps about confidence level)
- Officially, only C# and Python have Spotware-maintained SDKs/code samples; any other language (JavaScript/TypeScript, Java, Go, C++) is supported only in the generic sense that "any programming language" can open a TCP/TLS socket and speak Protobuf or JSON — [help.ctrader.com/open-api/](https://help.ctrader.com/open-api/)
- cAlgo (cBots, C#) is Spotware's own in-platform automation environment, separate from but related to the Open API; a community tutorial notes "cTrader automate (cAlgo) is based on C#... cTrader Automate API (cAlgo) is perfect for building automated trading robots" while OpenApiPy is the external Python path — [clickalgo.com/ctrader-python](https://clickalgo.com/ctrader-python)
- OpenAPI.Net's README states it "powers the popular cMAM software," which is cited by the maintainers as evidence of production use of the C# SDK specifically (per search-result summary of the repo README) — [github.com/spotware/OpenAPI.Net](https://github.com/spotware/OpenAPI.Net)
- From a community how-to-build-reliable-bots discussion pattern (cBotFactory-style guidance and forum norms): recommended operational practices include reviewing parameters and account exposure before each new bot instance (especially when the same logic runs across multiple symbols/accounts), because many apparent "market problems" are actually specification bugs (an ambiguous confirmation condition, an incorrect position-state check, or an unintended duplicate entry); starting with read-only/notification-only features before enabling live trade execution; requiring explicit confirevil for live orders; and logging every action so bot behavior is auditable — [cbotfactory.com/tutorials/ctrader-open-api-developer](https://www.cbotfactory.com/tutorials/ctrader-open-api-developer) (confidence caveat: this was retrieved via aggregated search summary, not a direct single-page fetch — treat the specific wording as approximate, though the substance is corroborated by the general tenor of forum troubleshooting threads reviewed in this research)
- The 2021 "Open API Critique" thread (see previous section) is itself evidence that experienced developers consider the raw SDK a leaky abstraction that forces understanding of "the right method in the right order" at the protocol level — meaning teams should invest in their own state-machine/sequencing layer around whichever SDK they pick, rather than assuming the SDK enforces safe call ordering — [community.ctrader.com/forum/connect-api-support/32091/](https://community.ctrader.com/forum/connect-api-support/32091/)

### Inferences
- Because the two official SDKs are both stale (last real commits mid-2024) and issues go unanswered, "official support" should not be the deciding factor between C# and Python — both are in the same boat. The practical decision driver is more likely to be: which language's protobuf/async ecosystem your team already trusts for long-running network services (e.g., .NET's Rx/async model vs. Python's Twisted-based async in OpenApiPy), since you will likely need to patch or extend the SDK yourself either way.
- Python's OpenApiPy uses Twisted (an older async framework, not asyncio), which is a notable operational detail: teams standardized on asyncio may find Twisted an awkward, less-familiar concurrency model to operate and debug in a 24/7 service — this is inferred from OpenApiPy's stated dependency on Twisted, not from an explicit community recommendation against it.
- The recurring "not an SDK for production" sentiment (Spotware's own 2021 admission) plus the multi-year issue backlog implies that regardless of language, a serious 24/7 system should plan for: vendoring/forking the SDK, writing comprehensive integration tests against a demo account, and not treating "it's Spotware's official library" as a stability guarantee.

### Gaps
- Could not find a direct, recent (2024-2026) forum or Reddit thread where experienced community members explicitly debate "Python vs C# vs Node vs Go for 24/7 unattended trading" with concrete pros/cons — this research did not surface such a head-to-head discussion despite targeted searches (e.g., no dedicated r/ctrader or algotrading subreddit thread was found; searches returned mostly official docs and forum index pages rather than opinion threads).
- Could not verify current GitHub star/usage trends as a popularity proxy for "which language the production community actually converged on" — the low star counts across all libraries (community and official alike) make it hard to infer a dominant choice with confidence.
- The claim about Protobuf vs JSON production guidance and the cBotFactory operational-practices list came from aggregated search summaries rather than a single directly-fetched primary page in this session; the general direction is plausible and consistent with official rate-limit/production framing, but the exact wording should be treated as approximate rather than a verbatim quote.

## What are the most frequently repeated pitfalls/lessons-learned about placing orders via the Open API?

### Takeaway
Across forum threads, the single most recurring theme is **volume-unit confusion** (the API's integer volume field is not "units" or "lots" directly — it is unit-count scaled by 100, i.e. "in cents"), closely followed by **price/precision rounding rejects** (stop loss/take profit/price values must match the symbol's `digits`, and relative SL/TP must be computed from that same precision) and **heartbeat/connection-timeout mistakes** (server disconnects after inactivity; a heartbeat must be sent — official guidance says **at least every 10 seconds**). A `timeInForce`-appears-to-be-ignored complaint also surfaced but investigation showed it was actually a client-side timestamp/format bug rather than a documented API quirk — still a useful cautionary pattern for how "the field is buggy" reports often turn out to be developer-side mistakes.

### Cited Findings
- **Volume units ("cents") — the most repeated pitfall:**
  - Per community discussion, `lotSize`, `minVolume`, `maxVolume`, and `stepVolume` on `ProtoOASymbol` are expressed in **cents of a unit**, e.g. a 100,000-unit lot size is represented as `10000000` in the field, so real units = field value / 100 — [community.ctrader.com/forum/connect-api-support/43672/](https://community.ctrader.com/forum/connect-api-support/43672/) (thread dated May 8, 2024)
  - In that same thread, a developer found the "divide by 100" rule that worked for `lotSize` gave a nonsensical result for `minVolume`/`maxVolume` ("this is wrong…"), and the thread ended with **no confirmed Spotware resolution visible** — flagging that even the "divide by 100" mental model isn't reliably consistent across all volume-related fields for every developer, so real code should sanity-check computed volumes against `stepVolume` bounds rather than trust a single hard-coded formula — [community.ctrader.com/forum/connect-api-support/43672/](https://community.ctrader.com/forum/connect-api-support/43672/)
  - Real-world consequence: a developer computing volume as `int(volume) * 100` for an intended size ended up sending only `1000` (way under the real minimum) and the order request silently hung/never executed; the fix was correcting the volume math to match the broker's actual minimum-volume requirement — [community.ctrader.com/forum/connect-api-support/41656/](https://community.ctrader.com/forum/connect-api-support/41656/)
  - A separate 2020 thread showed a user nearly misreporting a bug because they misjudged 1.01 lots vs. 1.0 lots against `stepVolume: 1000` / minimum volume `100,000` units — resolved as user error (insufficient real balance), but illustrative of how easy it is to get confused between "lots," "units," and the scaled protocol integer — [community.ctrader.com/forum/connect-api-support/23584/](https://community.ctrader.com/forum/connect-api-support/23584/) (May 2020)
  - A 2023 C# thread shows confusion computing `relativeStopLoss`/volume from pip distance differently for BTCUSD vs EURUSD (same 200-pip SL input produced relativeStopLoss of 2,000,000 for BTCUSD vs 2,000 for EURUSD) — a reminder that pip value/precision conventions are **not uniform across asset classes** (FX vs crypto vs metals) and formulas must be derived per-symbol from `ProtoOASymbol`, not hard-coded — [community.ctrader.com/forum/connect-api-support/40740/](https://community.ctrader.com/forum/connect-api-support/40740/) (Apr 29, 2023)
- **Price rounding / digits precision rejects:**
  - Community guidance: "the decimal places of your stop price must match with symbol digits, which you can get from `ProtoOASymbol`" — SL/TP with the wrong number of decimals get rejected — surfaced in relation to [community.ctrader.com/forum/connect-api-support/37007/](https://community.ctrader.com/forum/connect-api-support/37007/) ("Order price has more digits than symbol allows. Allowed 3 digits")
  - A related cBot-side thread shows an order rejected with error **"Relative stop loss has invalid precision"** — [community.ctrader.com/forum/cbot-support/16300/](https://community.ctrader.com/forum/cbot-support/16300/)
  - Community search results also surfaced reports that orders on symbols like XAUUSD/XAUEUR return "Invalid Request" specifically when take-profit/stop-loss carry decimal points on live trading, and that rounding a trailing-stop-loss value to one decimal place resolved rejections — reported via aggregated search of forum content (see Gaps re confidence)
  - A dedicated thread exists on exactly how to calculate `relativeTakeProfit`/`relativeStopLoss` correctly (round the price difference by the symbol's digits, then scale), indicating this is a repeated point of confusion serious enough to warrant its own how-to thread — [community.ctrader.com/forum/connect-api-support/37262/](https://community.ctrader.com/forum/connect-api-support/37262/)
- **Heartbeat / disconnect handling:**
  - Official FAQ: **"Applications are disconnected by the server after a period of inactivity. To avoid getting disconnected from the server, make sure that you send a heartbeat to the server at least once every 10 seconds."** — [help.ctrader.com/open-api/faq/](https://help.ctrader.com/open-api/faq/)
  - Forum clarification: a heartbeat message from the server is only sent *in response to* a client heartbeat — if the client never sends one, it will not receive one back either (i.e., silence is not itself a sign of a healthy idle connection) — [community.ctrader.com/forum/connect-api-support/36909/](https://community.ctrader.com/forum/connect-api-support/36909/) ("Heartbeats not coming when sending your own heartbeats")
  - Multiple dedicated threads exist specifically about keeping the connection alive with heartbeats in Python, and about general "Fix heartbeat and connection issues," and about disconnects every ~2 minutes with instant reconnect — indicating this is a recurring operational pain point across client implementations, not a one-off — [community.ctrader.com/forum/connect-api-support/36073/](https://community.ctrader.com/forum/connect-api-support/36073/), [community.ctrader.com/forum/fix-api/37923/](https://community.ctrader.com/forum/fix-api/37923/)
  - A separate thread clarifies that a "Trading Account is not authorized" error specifically means the connection/heartbeat is fine and the problem lies elsewhere (in account authorization sequencing) — useful for not misdiagnosing auth errors as connection/heartbeat problems — [community.ctrader.com/forum/connect-api-support/46693/](https://community.ctrader.com/forum/connect-api-support/46693/)
- **TimeInForce / expiration confusion (with an important caveat):**
  - A C#/OpenAPI.Net user reported (Oct 2023) that `TimeInForce` seemed to be ignored — orders always came back as GTC regardless of setting `ImmediateOrCancel` or `GoodTillDate`. **The actual root cause, per community diagnosis, was an incorrectly formatted `ExpirationTimestamp`** (needed to be a correct UTC Unix-milliseconds value via `((DateTimeOffset)DateTime.Now.AddDays(1)).ToUnixTimeMilliseconds()`), not a genuine bug in how the server handles `TimeInForce` — [community.ctrader.com/forum/connect-api-support/42171/](https://community.ctrader.com/forum/connect-api-support/42171/) (Oct 24–25, 2023)
  - Separately, the `ProtoOATimeInForce` enum itself includes `GOOD_TILL_DATE`, `GOOD_TILL_CANCEL`, `IMMEDIATE_OR_CANCEL`, and `FILL_OR_KILL` as valid values on `ProtoOANewOrderReq` — confirming the field is real/functional at the protocol level, and that the "ignored" report above was a client-side bug rather than evidence of a server-side defect — cross-referenced against Go protobuf definitions and cTrader message docs (search aggregation of [help.ctrader.com/open-api/messages/](https://help.ctrader.com/open-api/messages/) and third-party protobuf mirrors)
  - **Important distinction to flag explicitly:** cTrader's separate **FIX API** (not the Open API/protobuf protocol covered by this research) is documented elsewhere as ignoring whatever `TimeInForce` value a client sends and instead auto-assigning IOC for market orders, GTC for pendings without an expiration timestamp, and GTD for pendings with one. Because "cTrader FIX API" and "cTrader Open API" are frequently confused/conflated in casual forum discussion, teams should double check which API a given pitfall report is actually about — this research found the auto-redefinition behavior documented for FIX specifically, while the actual Open API bug report above turned out to be a timestamp formatting issue, not a documented auto-override policy for Open API's `TimeInForce`. Treat any specific claim that "Open API silently redefines your TimeInForce" as unconfirmed for the protobuf Open API unless independently re-verified against current server behavior.

### Inferences
- The recurring pattern across nearly every "order won't place / silently fails / rejected" thread is the same root shape: a client-side unit or precision mismatch (volume scale, price digits, or timestamp format) rather than a genuine server-side API defect. This suggests the highest-leverage defensive coding practice for a production system is **aggressive client-side validation against the live `ProtoOASymbol` data** (digits, pipPosition, minVolume/maxVolume/stepVolume, lotSize) immediately before constructing any `ProtoOANewOrderReq`, rather than trusting hard-coded conversion constants.
- Because at least one "the API ignored my parameter" bug report turned out to be user error, and the community/Spotware-staff response pattern in the critique thread was to acknowledge documentation gaps rather than deny them, a reasonable operating assumption is: **documentation gaps, not protocol bugs, are the dominant source of production incidents** in this ecosystem.
- The repeated existence of separate forum threads asking "how do I calculate relative SL/TP correctly" and "how do I calculate min/max volume correctly" suggests these two calculations are under-documented enough that a production system should write dedicated, well-tested utility functions for them (with unit tests against known symbols) rather than inlining the math ad hoc per order call.

### Gaps
- Could not directly confirm, from a single authoritative primary source fetched in this session, an official Spotware statement of the exact volume-scaling formula (i.e., a canonical "volume field = real units × 100" statement in the current official docs) — the /100 (or ×100) convention is reconstructed from multiple forum threads and examples rather than one clean documentation quote; a production implementer should verify this against the live `ProtoOASymbol` response for each symbol rather than relying solely on this note.
- Could not directly fetch the XAUUSD/XAUEUR decimal-rejection forum thread itself (only surfaced via aggregated search summary) — treat that specific claim as lower-confidence/needs re-verification against the primary thread.
- Did not find a forum thread specifically discussing "forgetting expiration leads to unexpected order persistence" as its own named pitfall (e.g., a pending order left open indefinitely because no expiration was set and the developer assumed one applied by default) — the closest evidence found is the general orders/expiration documentation stating pending orders without an expiry "remain active until triggered or cancelled manually," which supports the plausibility of this pitfall but no concrete forum incident report was located to confirm it happens in practice.
- Did not find a dedicated, heavily-repeated thread specifically about reconnect/resubscription mistakes (e.g., failing to re-subscribe to spot/depth feeds or re-send account auth after a reconnect) — heartbeat-to-avoid-disconnect was well evidenced, but "what exactly breaks if you reconnect without redoing the full auth handshake" was not directly confirmed in a single fetched thread.

## Are there any newer (2025-2026) changes to the Open API that older community posts/tutorials might not reflect?

### Takeaway
The one clearly-confirmed, dated, significant 2025-2026 development is **cTrader AI Agent Connect**, a pair of official Model Context Protocol (MCP) servers launched by Spotware on **May 14, 2026**, letting AI agents/tools (Claude Code, Cursor, ChatGPT Codex, Gemini CLI, etc.) execute trades and manage positions via natural language. This is presented as a **parallel, complementary path alongside the existing Open API and cBots — not a replacement** for either, so older Open API tutorials remain technically relevant, but anyone researching cTrader automation in 2026 will now also encounter MCP-related material that addresses a fundamentally different integration style (natural-language agent tool calls vs. direct protobuf/JSON requests) and should not conflate the two.

### Inferences
- Because MCP/AI Agent Connect is explicitly positioned as *not* a replacement for the Open API, older (pre-2026) Open API tutorials, Stack Overflow answers, and forum threads about protobuf message construction, authentication flow, and order placement should still be technically valid — the risk for someone researching in 2026 is more about **search/AI-answer contamination** (an LLM or search engine blending MCP-related material into an Open API query) than about the Open API protocol itself having silently changed underneath older guidance.
- The unresolved GitHub issue reporting `MessageFactory.GetMessage(ProtoMessage)` has no case for `ProtoOAOrderListRes` (opened **September 5, 2026** against OpenAPI.Net) suggests the live protobuf message surface has grown/changed since the SDK's June 2024 snapshot, and the SDK has not been updated to track it — concrete evidence that late-2024-and-earlier SDK-based tutorials may reference an incomplete message set relative to the current server.
