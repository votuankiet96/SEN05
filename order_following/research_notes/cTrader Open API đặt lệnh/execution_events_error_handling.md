# cTrader Open API — Execution Events, Error Handling, and Correlation/Idempotency

## What is the full structure of ProtoOAExecutionEvent, and what are all possible values of its executionType field? What triggers each?

### Takeaway
`ProtoOAExecutionEvent` is the single, universal asynchronous push message cTrader uses to report every order/position/deal/cash lifecycle change; it carries a required `executionType` enum (11 named values, numbered 2–12) plus optional nested `ProtoOAPosition`/`ProtoOAOrder`/`ProtoOADeal`/deposit-withdraw objects whose presence depends on which `executionType` fired.

### Cited Findings
- Full field list of `ProtoOAExecutionEvent` (from the primary protobuf source):
  - `optional ProtoOAPayloadType payloadType = 1 [default = PROTO_OA_EXECUTION_EVENT];`
  - `required int64 ctidTraderAccountId = 2;`
  - `required ProtoOAExecutionType executionType = 3;`
  - `optional ProtoOAPosition position = 4;`
  - `optional ProtoOAOrder order = 5;`
  - `optional ProtoOADeal deal = 6;`
  - `optional ProtoOABonusDepositWithdraw bonusDepositWithdraw = 7;`
  - `optional ProtoOADepositWithdraw depositWithdraw = 8;`
  - `optional string errorCode = 9;`
  - `optional bool isServerEvent = 10;`
  — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- Full `ProtoOAExecutionType` enum, verbatim comments (note: values start at 2; value 1 is not defined in the enum):
  - `ORDER_ACCEPTED = 2` — "Order passed validation."
  - `ORDER_FILLED = 3` — "Order filled."
  - `ORDER_REPLACED = 4` — "Pending order is changed with a new one."
  - `ORDER_CANCELLED = 5` — "Order cancelled."
  - `ORDER_EXPIRED = 6` — "Order with GTD time in force is expired."
  - `ORDER_REJECTED = 7` — "Order is rejected due to validations."
  - `ORDER_CANCEL_REJECTED = 8` — "Cancel order request is rejected."
  - `SWAP = 9` — "Type related to SWAP execution events."
  - `DEPOSIT_WITHDRAW = 10` — "Type related to event of deposit or withdrawal cash flow."
  - `ORDER_PARTIAL_FILL = 11` — "Order is partially filled."
  - `BONUS_DEPOSIT_WITHDRAW = 12` — "Type related to event of bonus deposit or bonus withdrawal."
  — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto); corroborated by [Model messages - Open API - cTrader Help](https://help.ctrader.com/open-api/model-messages/)
- `ProtoOAExecutionEvent` is documented as the async response to order-management requests that have no dedicated response message: `ProtoOANewOrderReq`, `ProtoOACancelOrderReq`, `ProtoOAAmendOrderReq`, `ProtoOAAmendPositionSLTPReq`, `ProtoOAClosePositionReq` — the API instead returns generic success (`ProtoOAExecutionEvent`) or error (`ProtoOAErrorRes`) — [Messages - Open API - cTrader Help](https://help.ctrader.com/open-api/messages/)
- `ProtoOAOrderStatus` enum (the status the nested `ProtoOAOrder.orderStatus` takes, related but distinct from `executionType`): `ORDER_STATUS_ACCEPTED = 1`, `ORDER_STATUS_FILLED = 2`, `ORDER_STATUS_REJECTED = 3`, `ORDER_STATUS_EXPIRED = 4` ("Might be valid for orders with partially filled volume"), `ORDER_STATUS_CANCELLED = 5` ("Might be valid for orders with partially filled volume") — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- `ProtoOADealStatus` enum (status on the nested `ProtoOADeal`): `FILLED = 2`, `PARTIALLY_FILLED = 3`, `REJECTED = 4` ("Deal is correct but was rejected by liquidity provider"), `INTERNALLY_REJECTED = 5` ("Deal rejected by server (e.g. no price quotes)"), `ERROR = 6` ("Deal is rejected by LP due to error (e.g. symbol is unknown)"), `MISSED = 7` ("Liquidity provider did not send response during execution period") — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- Official staff guidance: "For live real time update you should use execution event" (amusleh, Spotware staff) — [cTrader Forum - Open orders and positions](https://community.ctrader.com/forum/connect-api-support/37328/); confirmed again that ExecutionEvent also covers position modifications ("Yes, it does.") — [cTrader Forum - Real-time connection status monitoring & position open/close events](https://community.ctrader.com/forum/connect-api-support/36663/)
- Community-reported limitation: `ProtoOAExecutionEvent.payloadType` is always `PROTO_OA_EXECUTION_EVENT` (2126) regardless of the triggering action, so it cannot be used to tell "new order" vs "close position" events apart; Spotware staff (PanagiotisChar) advised checking `ProtoOAExecutionEvent.deal.closePositionDetail`, which is populated only when a position was closed — [cTrader Forum - PayloadType is not being transmitted to executionevent result](https://community.ctrader.com/forum/connect-api-support/40801/)

### Inferences
- Because `position`, `order`, `deal`, `depositWithdraw`, and `bonusDepositWithdraw` are all optional on the same envelope, client code must branch on `executionType` first and only then read the relevant nested object — e.g. `SWAP`/`DEPOSIT_WITHDRAW`/`BONUS_DEPOSIT_WITHDRAW` events are account-level cash events not tied to a client request and likely leave `order`/`position` unset.
- `ORDER_REJECTED` and `ORDER_CANCEL_REJECTED` most likely populate the event's own `errorCode` field (field 9) with a `ProtoOAErrorCode` name explaining why validation failed, since that field sits directly on `ProtoOAExecutionEvent` alongside `executionType`.
- The enum starting at 2 (no value 1) suggests a reserved/retired first value, but no source explains why.

### Gaps
- No official state-transition diagram/table was found confirming exactly which `executionType` values can legally follow which request type or each other (e.g., whether `ORDER_PARTIAL_FILL` can be followed later by `ORDER_EXPIRED` or `ORDER_CANCELLED` for the unfilled remainder — the `ProtoOAOrderStatus` comments imply this is possible, but no worked example was found).
- No official confirmation of whether a market order (which executes immediately rather than resting) receives a separate `ORDER_ACCEPTED` event before `ORDER_FILLED`, or goes straight to `ORDER_FILLED`/`ORDER_PARTIAL_FILL`. This is a plausible inference from market-order semantics but was not explicitly documented in any source reviewed.

## What is the structure of ProtoOAOrderErrorEvent / ProtoOAErrorRes, and what are the commonly encountered error codes? Is there an official enumeration of all error codes?

### Takeaway
There are **two parallel, non-overlapping error systems** in the Open API — a generic transport-level one (`ProtoErrorRes` / `ProtoErrorCode`) and a trading/account-level one (`ProtoOAErrorRes` and `ProtoOAOrderErrorEvent`, both carrying string codes drawn from `ProtoOAErrorCode`) — and Spotware's own API consumers have publicly flagged (in an open, unanswered GitHub issue) that this split is confusing and not clearly documented.

### Cited Findings
- `ProtoOAOrderErrorEvent` full field list: `optional ProtoOAPayloadType payloadType = 1 [default = PROTO_OA_ORDER_ERROR_EVENT];`, `required string errorCode = 2;`, `optional int64 orderId = 3;`, `required int64 ctidTraderAccountId = 5;`, `optional int64 positionId = 6;`, `optional string description = 7;` (field number 4 is not used/skipped) — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- `ProtoOAErrorRes` full field list: `optional ProtoOAPayloadType payloadType = 1 [default = PROTO_OA_ERROR_RES];`, `optional int64 ctidTraderAccountId = 2;`, `required string errorCode = 3;`, `optional string description = 4;`, `optional int64 maintenanceEndTimestamp = 5;`, `optional uint64 retryAfter = 6;` — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- Generic `ProtoErrorRes` (transport-level, distinct message) full field list: `optional ProtoPayloadType payloadType = 1 [default = ERROR_RES];`, `required string errorCode = 2;`, `optional string description = 3;`, `optional uint64 maintenanceEndTimestamp = 4;` — [OpenApiCommonMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiCommonMessages.proto)
- Both `errorCode` fields are typed as `string`, and documented as: "Contains name of ProtoErrorCode or other custom ErrorCodes" — [OpenApiCommonMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiCommonMessages.proto)

- Real-world trading error example independently confirmed on the forum: `TRADING_BAD_VOLUME` fires with description "Order volume 0.10 is smaller than group minVolume=1.00" — [cTrader Forum thread on bad volume](https://community.ctrader.com/forum/ctrader-algo/40296/) (via search snippet)
- Official error-handling doc lists example error-triggering scenarios (not a full enumeration): "Attempting to place an order for a symbol for which the market is closed", "Sending an incorrect or an unsupported message", "Attempting to modify an order that is being executed", "Sending a message after losing your connection to the cTrader backend"; it states "the full list of all supported error codes" lives in the `ProtoErrorCode` enum, but does not reproduce it on the page itself — [Error handling - Open API - cTrader Help](https://help.ctrader.com/open-api/error-handling/)
- **Documentation gap acknowledged by the community**: GitHub issue opened by user "fgnm" (March 2025) states error codes/messages are "not clear or well documented," notes two message types exist — `ProtoOAErrorRes` (payload within `ProtoMessage`, type 2142) and `ProtoErrorRes` (received directly on the TCP socket) — and explicitly asks "Is it really possible to receive a `ProtoErrorRes`? When? Why?" plus requests a combined list explaining why `ProtoOAErrorCode` and `ProtoErrorCode` are separate. As observed during this research, the issue was **still open with no visible response from Spotware maintainers** — [Error codes and error messages are not clear or well documented · Issue #30](https://github.com/spotware/openapi-proto-messages/issues/30)

### Inferences
- Because `errorCode` is a `string` field rather than a typed enum on the wire, Spotware can add or change server-side error codes without a breaking schema change; client code should treat unrecognized error-code strings defensively rather than assuming the published enum is exhaustive/final.
- `MARKET_CLOSED` exists only in the generic `ProtoErrorCode` (=9), not in `ProtoOAErrorCode`; trading-specific "can't trade now" conditions on the OA side appear to instead use `TRADING_DISABLED` (132) or `TRADING_NOT_ALLOWED` (133) — but which one a given "market closed" order-rejection actually returns is not confirmed (see Gaps).

### Gaps
- No single official "master list" unifying `ProtoErrorCode` and `ProtoOAErrorCode` was found; per GitHub issue #30, this is a confirmed, acknowledged (by an external developer) documentation gap, unresolved by Spotware at time of research.
- It is not confirmed whether `ProtoOAErrorRes.errorCode` can carry values from the generic `ProtoErrorCode` enum as well as `ProtoOAErrorCode` (the issue-30 reporter claims to have observed this during a maintenance window, but Spotware has not confirmed it).
- Not confirmed which exact `ProtoOAErrorCode` value is returned for a "market closed" order rejection specifically (vs. the generic `MARKET_CLOSED` used elsewhere in the protocol).

## How does a client correlate an async ExecutionEvent or ErrorEvent back to the specific ProtoOANewOrderReq that caused it? What is the exact sequence of messages after sending one new-order request?

### Takeaway
Correlation works on two independent levels — the transport-level `clientMsgId` on the `ProtoMessage` envelope (client-assigned, echoed back verbatim on whatever response/event answers that call) for immediate request↔first-response matching, and the domain-level `orderId`/`positionId`/`dealId` embedded inside the execution event's nested objects for tracking an order across its whole lifecycle — but neither `ProtoOAExecutionEvent` nor `ProtoOAOrderErrorEvent` carries its own `clientMsgId` field, so multi-step correlation (e.g., the later `ORDER_FILLED` that has no relation to the original request's envelope) must be done by matching `orderId`, not `clientMsgId`.

### Cited Findings
- `ProtoMessage` (the outer envelope for every message) fields: `required uint32 payloadType = 1` ("Contains id of ProtoPayloadType or other custom PayloadTypes"), `optional bytes payload = 2` ("Serialized protobuf message that corresponds to payloadType"), `optional string clientMsgId = 3` ("Request message id, assigned by the client that will be returned in the response") — [OpenApiCommonMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiCommonMessages.proto), corroborated by [Common messages - Open API - cTrader Help](https://help.ctrader.com/open-api/common-messages/)
- Neither `ProtoOAExecutionEvent` nor `ProtoOAOrderErrorEvent` defines a `clientMsgId` field in their own payload — it only exists on the wrapping `ProtoMessage` — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- `ProtoOAOrderErrorEvent` directly carries `orderId` and `positionId` (plus `ctidTraderAccountId`) so it can be matched to known orders/positions without needing `clientMsgId` — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- `ProtoOANewOrderReq` itself carries client-supplied identifiers that get echoed onto the resulting order: `optional string label = 16;`, `optional string clientOrderId = 18;` — and `ProtoOAOrder` (nested in later execution events) carries `optional string clientOrderId = 17;`, allowing a client to tag a request and later recognize the resulting order even without `clientMsgId` — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto) / [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- Official client-library pattern for correlation (OpenAPI.Net, C#): subscribe to the `ProtoMessage` stream, and read `protoMessage.ClientMsgId` off each incoming message to match it to the request that set it — [Open Client - OpenAPI.Net](https://spotware.github.io/OpenAPI.Net/open-client/) (via search synthesis)
- Two distinct request/update mechanisms are officially recommended for different purposes: `ProtoOAReconcileReq` for pulling "a trader's current open positions and pending orders" as a point-in-time snapshot, versus `ProtoOAExecutionEvent` for "live real time update" — stated directly by Spotware staff "amusleh" — [cTrader Forum - Open orders and positions](https://community.ctrader.com/forum/connect-api-support/37328/), [cTrader Forum - How to get the positionId using openApiPy?](https://community.ctrader.com/forum/connect-api-support/37689/)
- `ProtoOAExecutionEvent` is generically documented as the async response to `ProtoOANewOrderReq` (and the other order-management requests) since these requests have no dedicated response message of their own — [Messages - Open API - cTrader Help](https://help.ctrader.com/open-api/messages/)

### Inferences
- The intended/likely sequence for a **new pending order** is: (1) client sends `ProtoOANewOrderReq` wrapped in a `ProtoMessage` with a chosen `clientMsgId`; (2) if validation passes, the server sends back a `ProtoOAExecutionEvent` with `executionType=ORDER_ACCEPTED` and a populated `order` object (this is the message whose enclosing `ProtoMessage.clientMsgId` should match the request, giving the client the new `orderId`); (3) at some later, indeterminate time (seconds to days later, or never), when the order's trigger condition is met, the server sends one or more further `ProtoOAExecutionEvent`s with `executionType=ORDER_FILLED` or `ORDER_PARTIAL_FILL` — these later events are **not** responses to the original request in a `clientMsgId` sense (they arrive on their own, unsolicited `ProtoMessage`, likely without a `clientMsgId` at all, since nothing the client sent triggered them), so the client must match them to the original order via `order.orderId`/`position.positionId`, which it captured from step 2.
- If the initial request instead fails validation, the client receives either a `ProtoOAExecutionEvent` with `executionType=ORDER_REJECTED` and `errorCode` populated, or a `ProtoOAErrorRes` — the precise conditions under which the API chooses one over the other, versus emitting a `ProtoOAOrderErrorEvent` instead, are not clearly documented anywhere found (see Gaps); this is a synthesis from the message shapes and general docs, not a directly documented flow diagram.
- For a **market order** (which is meant to execute immediately rather than rest), it is plausible the accept-then-fill two-step above collapses to a single `ProtoOAExecutionEvent` with `executionType=ORDER_FILLED` (or `ORDER_PARTIAL_FILL`) directly — but this was not explicitly confirmed in any source (see Gaps in the first question above).

### Gaps
- No official sequence diagram or worked example (e.g., a docs page showing the literal two `ProtoOAExecutionEvent` payloads for one new order) was found describing the exact accept→fill message sequence end-to-end.
- The precise decision rule for when the server returns a top-level `ProtoOAErrorRes` vs. a `ProtoOAOrderErrorEvent` vs. a `ProtoOAExecutionEvent(executionType=ORDER_REJECTED)` for a failed `ProtoOANewOrderReq` is not documented; this ambiguity is the same one flagged by the community in GitHub issue #30.
- Whether `clientMsgId` is preserved/forwarded onto later, unsolicited execution events for the same order (e.g., the `ORDER_FILLED` that arrives long after the original `ORDER_ACCEPTED` response) or is only ever echoed on the first/direct response was not explicitly confirmed by any source — official docs only say clientMsgId "will be returned in the response," which is ambiguous for events with no single triggering request.

## Does cTrader's server implement any deduplication if the same order request is sent twice, or is that entirely the client's responsibility?

### Takeaway
No official Spotware documentation was found describing server-side deduplication of repeated `ProtoOANewOrderReq` messages (whether by `clientMsgId`, `label`, or `clientOrderId`); every relevant source treats duplicate-order prevention as the caller's/cBot's own responsibility, and community threads about duplicate orders describe purely client-side causes and client-side fixes.

### Cited Findings
- `clientMsgId` is documented solely as a correlation mechanism ("Request message id, assigned by the client that will be returned in the response") with no mention of dedup/idempotency semantics — [OpenApiCommonMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiCommonMessages.proto)
- `label` is documented as "an identifying string associated with an order or position;" when the order is filled, the resulting position carries the same label, and it "can be used as a unique identifier for the position to be managed later" — this is framed as a client-side bookkeeping convenience, not a stated server-enforced uniqueness/dedup constraint — [cTrader Forum - Labels and a New Method to Create Orders](https://community.ctrader.com/forum/announcements/479/) (via search synthesis)
- `ProtoOANewOrderReq.clientOrderId` (field 18, optional string) and its echo on `ProtoOAOrder.clientOrderId` (field 17) exist, but no source found documents any server-side uniqueness check or rejection behavior if the same `clientOrderId` (or `label`) is reused across two separate requests — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- Duplicate-order incidents reported in the (cBot/cAlgo, not raw Open API, but same underlying platform) community are consistently attributed to client-side logic — e.g., calling `MarketData.GetSeries()` inside `OnBar` causing `OnBar` to re-fire and resend an order, or `OnTick()` firing rapidly before a local "already traded" flag updates — with community-suggested fixes being entirely client-side (checking `Trade.IsExecuting` before sending, updating a local anchor variable immediately after sending) rather than any mention of the server rejecting/collapsing the duplicate — [cTrader Forum - Duplicate orders onbar method](https://community.ctrader.com/forum/cbot-support/12194/), [cTrader Forum - Multiple duplicate position Opened -- Issue](https://community.ctrader.com/forum/ctrader-algo/13457/), [cTrader Forum - How to avoid onTick() running 'too quick' to place 'duplicate orders'](https://community.ctrader.com/forum/cbot-support/35186/)
- No mention of idempotency keys, dedup windows, or "already processed" error codes was found in the `ProtoOAErrorCode`/`ProtoErrorCode` enums extracted above, nor in the error-handling doc's list of error scenarios.

### Inferences
- Given the complete absence of any documented idempotency key or dedup mechanism, and that the only identifiers available (`clientMsgId`, `label`, `clientOrderId`) are documented purely as correlation/bookkeeping aids, sending the same logical `ProtoOANewOrderReq` twice (e.g., after a client-side timeout with no confirmed response) should be assumed to create two independent orders/positions rather than being collapsed into one by the server. This is an inference from the absence of contrary documentation, not a confirmed test result or explicit Spotware statement.

### Gaps
- No official Spotware statement was found either confirming or explicitly denying server-side deduplication for rapidly repeated, identical `ProtoOANewOrderReq` messages (e.g., same `label`/`clientOrderId` sent twice within milliseconds due to a client retry).
- Whether `clientOrderId` is required to be unique per account (and what happens if it is reused — silently accepted, rejected with an error, or ignored) is not documented in any source found.
- No dedicated Open-API-specific (as opposed to cBot/cAlgo local-execution) forum thread or GitHub issue specifically testing "send the exact same ProtoOANewOrderReq twice" was found in this research pass.

## What happens on partial fills — does the API send multiple execution events for one order, and how should remaining/filled volume be tracked?

### Takeaway
Yes — each partial fill increment is delivered as its own `ProtoOAExecutionEvent` with `executionType=ORDER_PARTIAL_FILL`, carrying both a per-increment `ProtoOADeal` and the order's updated cumulative fill state, so clients should track remaining volume from the order's cumulative `executedVolume` field (requested volume minus `executedVolume`) rather than by manually summing deal events.

### Cited Findings
- `ProtoOAExecutionType.ORDER_PARTIAL_FILL = 11` — "Order is partially filled." — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- `ProtoOAOrder` (nested in the execution event) includes `optional double executionPrice = 7;` and `optional int64 executedVolume = 8;` — representing the order's cumulative filled volume, separate from the originally requested `volume` on `ProtoOANewOrderReq` — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto), [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto)
- `ProtoOADeal` (the per-fill record nested in the execution event) has both `required int64 volume = 4;` and `required int64 filledVolume = 5;`, plus its own `required ProtoOADealStatus dealStatus = 12;` — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- `ProtoOADealStatus` includes a distinct `PARTIALLY_FILLED = 3` value (separate from `FILLED = 2`), confirming deals themselves can be partial — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)
- `ProtoOAOrderStatus.ORDER_STATUS_EXPIRED` and `ORDER_STATUS_CANCELLED` doc comments both explicitly state "Might be valid for orders with partially filled volume," confirming an order can still expire or be cancelled after receiving one or more partial fills (leaving the filled portion as a position while the remainder is dropped) — [OpenApiModelMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto)

### Inferences
- The robust client-side tracking pattern implied by the schema is: on every `ORDER_FILLED`/`ORDER_PARTIAL_FILL` event, read `order.executedVolume` (cumulative total filled so far) and compute `remaining = requestedVolume - order.executedVolume`; use the accompanying `deal.filledVolume`/`deal.volume` only for building a per-fill trade blotter (e.g., for commission/VWAP calculations), not as the authoritative running total — relying on `order.executedVolume` is more robust to a potentially missed intermediate event than manually summing individual deals.
- Because `ORDER_FILLED` and `ORDER_PARTIAL_FILL` are distinct `executionType` values (and `ProtoOAOrderStatus` has only one `ORDER_STATUS_FILLED`, with no separate "fully vs. partially filled" status), the fill increment that completes an order should arrive as `executionType=ORDER_FILLED` (not another `ORDER_PARTIAL_FILL`) — inferred from the enum design, not from a documented worked example.

### Gaps
- No official worked example/sequence diagram was found showing the literal two-or-more `ProtoOAExecutionEvent` payloads for a single order filled in multiple increments (e.g., a 3-lot order filled as 1 lot then 2 lots).
- Not confirmed whether the unfilled remainder of a partially filled order that subsequently expires/is cancelled generates its own follow-up execution event referencing the same `orderId` with `executionType=ORDER_EXPIRED`/`ORDER_CANCELLED` — the `ProtoOAOrderStatus` comments imply this scenario is possible but no concrete example was found.

## Are there known community-reported edge cases or bugs in execution event delivery (e.g., missed events after reconnect, out-of-order delivery)?

### Takeaway
The clearest, confirmed community-reported issue is that `ProtoOAExecutionEvent.payloadType` cannot be used to distinguish the triggering action (it is always `PROTO_OA_EXECUTION_EVENT`); beyond that, no Spotware-acknowledged bug reports of missed events after reconnect or out-of-order delivery were found in this pass, but the platform's own guidance (recommending a pull-based reconcile request and a mandatory heartbeat) implicitly signals that clients should not assume the event stream is complete or gap-free across a disconnect.

### Cited Findings
- Confirmed bug/limitation: a developer found `ProtoOAExecutionEvent`'s `payloadType` always reports `PROTO_OA_EXECUTION_EVENT` (2126), never differentiating e.g. "order opened" from "position closed"; Spotware staff "PanagiotisChar" responded with the workaround of checking `ProtoOAExecutionEvent.deal.closePositionDetail`, which is populated only when a position was closed — not fixed at the protocol level, only worked around — [cTrader Forum - PayloadType is not being transmitted to executionevent result](https://community.ctrader.com/forum/connect-api-support/40801/)
- Confirmed, still-open documentation gap: GitHub issue #30 on error-code clarity (see error-codes section above) remained unanswered by Spotware maintainers at the time of this research, indicating at least this class of developer-facing confusion is unresolved — [Issue #30, spotware/openapi-proto-messages](https://github.com/spotware/openapi-proto-messages/issues/30)
- Official recommendation to use `ProtoOAReconcileReq` ("request for getting a trader's current open positions and pending orders") as the mechanism for obtaining authoritative current state, positioned as distinct from and complementary to relying on the live `ProtoOAExecutionEvent` stream — stated by Spotware staff "amusleh" — [cTrader Forum - Open orders and positions](https://community.ctrader.com/forum/connect-api-support/37328/)
- FAQ instructs clients to send an application-level heartbeat "at least once every 10 seconds" to avoid being disconnected for inactivity, implying disconnects are an expected, normal, and client-manageable occurrence — [FAQ - Open API - cTrader Help](https://help.ctrader.com/open-api/faq/)
- The forum thread most directly on-topic for "real-time connection status monitoring & position open/close events" contains only high-level guidance ("use ExecutionEvent," "monitor the socket connection for status changes") from Spotware staff "amusleh," and explicitly does **not** address missed-events-after-reconnect, out-of-order delivery, or reconciliation strategy in any depth — [cTrader Forum - Real-time connection status monitoring & position open/close events](https://community.ctrader.com/forum/connect-api-support/36663/)
- No sequence-number, delivery-guarantee, or "resend on reconnect" field/mechanism was found on `ProtoOAExecutionEvent` or `ProtoMessage` in the protobuf schema itself (its only fields are `payloadType`, `payload`, `clientMsgId`) — [OpenApiCommonMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiCommonMessages.proto)

### Inferences
- The absence of any sequence-number or gap-detection field, combined with Spotware's own advice to use `ProtoOAReconcileReq` for authoritative state, strongly suggests the Open API provides **no formal delivery guarantee** (no documented at-least-once or exactly-once semantics, no queued replay) for execution events generated while a client is disconnected — i.e., a client should treat every reconnect as an opportunity to reconcile via a fresh pull rather than assume the event stream "caught it up" automatically. This is inferred from the absence of contrary evidence and the shape of the available tooling (reconcile request existing at all implies it's needed), not from a direct Spotware statement of the guarantee level.

### Gaps
- No official Spotware documentation or forum post explicitly confirms or denies out-of-order delivery of execution events within a single, continuously connected session.
- No official Spotware documentation explicitly states that events generated while disconnected are dropped (vs. queued and replayed on reconnect) — this is inferred, not confirmed, and no direct test report was found either way.
- This research pass did not exhaustively search the issue trackers of `spotware/OpenApiPy`, `spotware/OpenAPI.Net`, or `spotware/connect-protobuf-messages` specifically for tickets tagged around "missed execution event" or "out of order delivery" beyond the general web searches performed; a deeper, issue-tracker-specific search (e.g., using GitHub's own search/`gh` CLI across all Spotware Open-API repos) could surface more community-reported cases than were found here.

## Additional note on rate limits (context for correlation/retry behavior)
- Confirmed directly from the primary "Getting started" page: "You can perform a maximum of 50 requests per second per connection for any non-historical data requests" and "a maximum of 5 requests per second per connection for any historical data requests," and these limits apply per connection "no matter how many users are authorized through it" — [Getting started - Open API - cTrader Help Centre](https://help.ctrader.com/open-api/)
- `ProtoOAErrorRes` includes a `retryAfter` field (uint64, field 6) alongside `errorCode`/`description`/`maintenanceEndTimestamp`, and a rate-limit breach is reported to return a 429-style response with this retry-after value indicating how long to wait before the next request — [OpenApiMessages.proto](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiMessages.proto); rate-limit error code likely corresponds to `ProtoOAErrorCode.REQUEST_FREQUENCY_EXCEEDED = 108` or the generic `ProtoErrorCode.BLOCKED_PAYLOAD_TYPE = 11` ("rate limit is reached") — this specific mapping (which of the two codes is actually returned for a 429) is an inference, not directly confirmed by a source.
